1. Purpose & Scope

This annex extends the SPARTA PDR baseline with the security, safety and assurance content needed to bridge Preliminary Design Review to Critical Design Review. It supersedes informal notes in Deliverables 01–04 and is the authoritative source for:

  • The cyber threat model (adversary classes, attack paths, controls, residual risk, verification hooks).
  • The preliminary hazard log (PHL) with severity, likelihood, mitigations, and owners.
  • The top-level safety/security assurance case (goal decomposition, evidence, confidence).
  • Consequence analysis for false positive and false negative trust verdicts.
  • The authority boundary matrix between SPARTA, MARS, TSOC and C2 (who can do what, under what authority).
  • Fail-safe and degraded-state behavior, including policy-controlled action limits.
  • Contract-grade interface schemas (mandatory/optional fields, enums, versioning, replay rejection, classification markings, signature binding, idempotency).
  • Acceptance-criteria sharpening for previously under-specified SYS-* requirements.
  • The CDR closure criteria and the explicit list of open points with owners.
Normative Precedence Where this annex refines or tightens a SYS-* requirement, the tightened acceptance criterion becomes the authoritative wording for CDR and for qualification. Deliv. 02 requirement text is unchanged; the tightening is captured as an acceptance-criterion sub-clause with a clear reference tag (AC-<SYS-ID>). No requirement is weakened by this annex.

2. Product Framing

SPARTA is the product. It is a platform-agnostic, mission-aware cyber trust layer hosted on distributed tactical edge nodes and integrated upward into Tactical Security Operations Centres (TSOC) and laterally with the MARS mission system. SPARTA is not a host platform, airframe, weapons system or C2 authority.

The Eurodrone-class MALE RPAS is used in this datapack as the reference edge-node integration case because it is a credible European multi-nation platform with public contract status and a mission-systems profile that exercises SPARTA's distributed, contested-network assumptions. It is one of several candidate hosts; the technical baseline is written to remain valid on rotary-wing tactical nodes, wheeled ground mission-management nodes, remote-carrier-class UAS, and future Combat Cloud edge appliances.

AuthoritySPARTA produces advisory trust verdicts and bounded recommendations. Mission-effect authority remains with MARS / C2."SPARTA disconnects the platform" or "SPARTA takes over."
Scope of protectionSPARTA protects the trust of mission-critical data flows and states at the edge; it is not a boundary firewall or a COMSEC box."SPARTA replaces the cryptographic subsystem."

5.1 Confidence Statement

At PDR baseline, the confidence position is:

  • G1 (bounded/explainable): High — advisory-only design is constitutional; interface contracts (§11) structurally prevent SPARTA from issuing C2-actionable commands.
  • G2 (resilience to 8 adversary classes): Medium-high — controls defined and mapped; verification plan written (§13) but full red-team campaign executes in CDR window.
  • G3 (fail-safe): High — explicit SYS-SAFE-003 and §8; test evidence pending in V-model phase 3.
  • G4 (authority boundary): High — enforced in architecture (§7) and interface contracts.
  • G5 (operator UX under stress): Medium — HFE validation V-HFE-01 is scheduled but not yet executed at PDR. Lowest-confidence sub-goal; flagged for CDR.

8. Fail-safe & Degraded-state Behavior

SPARTA's fail-safe principle is "fail to unknown, not to trusted". When SPARTA cannot produce a high-confidence trust verdict, it must never silently emit "trusted"; it must declare "unknown", degrade mode, and signal the degrade to MARS and TSOC.

Nominal (Mode A)All controls greenFull trust objectNormal UIFull trust objectPeriodic heartbeat
Degraded (Mode B)Neighborhood consensus unavailable OR freshness TTL near breachFull trust object with "degraded" flag + reduced confidenceAmber banner + reasonAccepts degraded with reduced weightAlarm with reason code

10.2 IF-EXT-01 — MARS ↔ SPARTA

  • Direction: SPARTA → MARS (advisory, trust_object, health); MARS → SPARTA (mission_instance_id, mission phase, policy scope).
  • Payload classes:trust_object, advisory, health from SPARTA; mission_scope from MARS.
  • Mandatory fields in advisory:advisory_id, target_asset, severity (info|low|medium|high|critical), confidence (0.0–1.0), explanation_ref, recommended_actions[] (enum-bounded).
  • Recommended actions enum:observe, increase_cadence, cross_check, downgrade_trust, request_quarantine. No direct-effector actions (§9).
  • Versioning: schema major.minor; consumers MUST accept same major, MUST reject older major, SHOULD accept newer minor with unknown-fields-ignored rule.
  • Freshness: MARS MUST reject objects with expired freshness_ttl_ms relative to receive time + bounded skew (±250 ms default).
  • Replay rejection: MARS MUST reject duplicate message_id within a sliding 10-minute window per source.
  • Idempotency: advisories are idempotent on message_id; re-delivery MUST be silently deduplicated (§10.7).

10.3 IF-EXT-02 — Peer ↔ Peer (PeerSummary)

  • Direction: bidirectional between accredited peers in Mode B.
  • Payload:peer_summary — compact, < 4 kB nominal / < 8 kB hard cap (SYS-PERF-002).
  • Mandatory fields:peer_id, reputation_vector, observation_window (ISO-8601 duration), sensor_class_coverage[], policy_bundle_version.
  • Sybil control:peer_id is certificate-bound; one live session per peer_id; CA-level rate limit.
  • Staleness: default freshness TTL 3 s; peers MUST reject on expiry.
  • Policy-skew handling: accept at most 1 minor policy version delta; reject and signal policy_skew beyond that.
  • Replay rejection: monotonic nonce per peer_id; hard-reject on non-monotonic.

10.4 IF-EXT-03 — TSOC ↔ SPARTA

  • Direction: SPARTA → TSOC (evidence, trust_object, advisory, health, adjudication_request); TSOC → SPARTA (policy_bundle, adjudication_result, quarantine_directive).
  • Critical types:
    • policy_bundle: signed, version-stamped, release-caveated (§10.6). Nodes verify with pinned TSOC issuer cert.
    • adjudication_request: sent when the node cannot reach a high-confidence verdict locally. Required fields: request_id, evidence_refs[], neighborhood_state, deadline_ms.
    • adjudication_result: idempotent on request_id — re-delivery within deadline MUST be deduplicated; late delivery after deadline is treated as not received.
  • Break-glass: rollback/override only with a two-person-rule-signed directive; node rejects otherwise.

10.5 IF-EXT-04 — Cross-Domain Release (sanitizer)

  • Sanitizer rules: deny-by-default; accept only objects with both classification and releasability matching the target domain's accreditation.
  • Transform: sanitizer MAY redact fields flagged redact_if_released_to; redaction is recorded in audit; the signed object is re-wrapped with sanitizer provenance.
  • Attribute preservation:source_node_id is replaced with an accredited pseudonymous handle when crossing to a lower-trust domain; the mapping is retained at TSOC.
  • Audit: every release decision is appended to an append-only audit stream; non-release is also logged with reason code.

10.6 IF-EXT-05 — PolicyBundle delivery

  • Envelope: as §10.1 with payload_type = "policy_bundle".
  • Payload mandatory fields:bundle_id, bundle_version (SemVer), monotonic_counter, build_provenance (SLSA link), applicable_fleets[], release_caveats[], shadow_mode (true|false), rollback_target (bundle_version or null).
  • Version discipline: nodes reject bundles with monotonic_counter ≤ last-installed unless accompanied by a two-person-rule-signed break-glass object.
  • Shadow mode: when shadow_mode = true, the bundle is evaluated but emits no external advisory; MOE-regression detector gates promotion.
  • Signature: PQ-ready alg profile (Dilithium3 or ECDSA-P384 fallback). Issuer cert pinned; rotation via signed key-rollover object.

10.6bis IF-EXT-06 — TSOC malware-verdict service (Orion Malware®-class)

  • Direction: SPARTA → TSOC (file artefact); TSOC → SPARTA (signed verdict).
  • Payload types: malware_artefact_submission (out), malware_verdict (in).
  • Verdict mandatory fields: verdict_id (UUID, idempotency key), artefact_hash_sha384, verdict (enum: clean, suspicious, malicious, pup, inconclusive), confidence (0.0–1.0), ioc_updates[], valid_until.
  • Ingestion: realizes SYS-IF-006. Idempotent on verdict_id within a 10-min window; duplicate deliveries MUST NOT re-apply IOC changes.
  • IOC store update: treated as signed content under SYS-DC-005 — signature validated, staged, hot-swapped, rollback-capable.
  • DDIL behaviour: submissions and verdicts queued; verdicts arriving after valid_until are logged and discarded.

10.6ter IF-EXT-05 — Accredited identity provider (CymID®-class)

  • Direction: identity provider ↔ SPARTA (provisioning, rekey, revocation).
  • Payload types: identity_binding, crl_update, ocsp_response, key_rollover.
  • Mandatory fields (identity_binding): subject (node-ID / operator-ID / peer-ID), cert_chain[], accredited_ca_id, validity_start, validity_end, role, revocation_epoch.
  • Revocation: realizes SYS-IF-007. Node MUST honour revocation within AC-SYS-SEC-001 latency (≤ 30 s nominal backhaul).
  • Provider unavailable: SPARTA continues against cached CRL/OCSP until expiry, then fail-unknown.
  • Break-glass re-key: authorized per §7 (TSOC + Security-C2 co-sign); logged under SYS-DC-002.

10.7 Idempotency & replay

Every SPARTA message is idempotent on message_id. Re-delivery within the replay window MUST be deduplicated and MUST NOT cause a state change at the consumer. Policy / adjudication messages additionally have:

  • At-least-once delivery is assumed across contested links.
  • Exactly-once semantics at the application layer are provided by message_id deduplication in a bounded window (default 10 min).
  • Late messages (arriving after their freshness_ttl_ms) are dropped with an audited late_drop event.
  • Monotonic counters prevent downgrade/rollback on policy bundles and epoch keys.

10.8 Signature & provenance binding

The provenance_hash in the envelope binds source_node_id, timestamp_utc, nonce, and the canonical form of payload. This makes cut-and-paste attacks (swap payload, keep old signature) structurally infeasible. The algorithm profile is crypto-agile: ECDSA-P384-SHA384 is the baseline; Ed25519 is allowed for size-constrained paths; Dilithium3 is the post-quantum forward profile.

10.9 Cross-domain sanitization rules

Sanitization is a replacement operation, not a redaction-only operation. The sanitizer:

  • Strips handling_caveats not admissible in the target domain.
  • Rewrites source_node_id to an accredited pseudonymous handle.
  • Drops fields marked redact_if_released_to for the target.
  • Re-signs the resulting object with a sanitizer-specific key.
  • Appends a sanitizer provenance record to the audit stream.
  • Refuses to release if any mandatory marking is missing.

15.2 Glossary (excerpt — full glossary in index.html §8)

TermMeaning in SPARTA context
AdvisoryAn explainable, bounded recommendation emitted by SPARTA to MARS/TSOC/operator. Never a direct effector command.
Break-glassA two-person-signed override that permits rollback or other monotonicity-breaking actions under accreditation oversight.
Coalition tierAccreditation tier of a peer; governs cross-domain release and reputation propagation.
Degraded / Minimum / Fail-unknownThree non-nominal SPARTA modes, in decreasing order of capability — see §8.
EvidenceRaw observation from a local sensor (net/host/mission-bus). Not yet trust.
Freshness TTLThe interval after which a SPARTA object is treated as stale by any consumer.
MARSOn-platform virtualization layer (hypervisor / container-orchestration environment on the drone host). Previously labelled "Mission Authority and Routing Service" in earlier drafts — that meaning is superseded as of Draft C.1. Mission authority lives with Command C2 (see Authority Matrix §7).
Edge nodesPBS component #3. Tactical platforms (airborne or ground-mobile) hosting the SPARTA Edge Agent. Reference class: Eurodrone-class RPAS.
Fog nodesPBS component #4. Intermediate compute tier hosting the optional Mode-B-peer tactical correlator; not required for baseline.
Command C2PBS component #6. Ground mission command — engagement / mission-change / physical-link-disconnect (mission scope) / mission-end authority. Subsumes the ground mission-planning function formerly labelled MGS in Draft C.1..C.2.
Security C2PBS component #7. Ground defensive-cyber command. Coordinates fleet-level cyber response; concurs on PolicyBundle release and node quarantine. Distinct from Command C2.
FCSFlight Control System — safety-critical avionics. Authority-only (not a PBS component): SPARTA receives read-only telemetry over IF-EXT-04 and has no write path to FCS. SYS-DC-001 hard boundary.
MGS (deprecated label)Formerly "Mission Ground Segment / Control System" in Draft C.1..C.2. As of Draft C.3, the mission-planning function is folded into Command C2; MGS is no longer a standalone entity in the PBS or Authority Matrix.
Airbus TSOCReference upstream Security Operations Centre. Hosts alert ingestion, analyst cockpit, incident investigation, Orion Malware® file analysis (IF-EXT-06), CymID®-class identity service (IF-EXT-05), response orchestration, rule-update push and remote forensic pull.
PolicyBundleSigned, versioned, release-caveated ruleset delivered from TSOC to nodes.
Provenance hashBinding of source identity + timestamp + nonce + payload; prevents cut-and-paste signature reuse.
Reference integration caseA specific host class (Eurodrone illustrated) used to exercise SPARTA's platform-agnostic baseline. Not the SPARTA product itself.
Shadow modePolicyBundle evaluation state in which no external advisory is emitted, used to gate rollout by MOE regression.
Trust objectA signed, bounded, explainable statement by SPARTA about the trust state of an asset at a time.
TSOCTactical Security Operations Centre — accreditation, policy authoring, incident authority.
